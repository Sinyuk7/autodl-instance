# Review 任务指南 · autodl-instance

> 给下一个 reviewer 的元指南。
> 不是 review 报告本身，是**告诉你怎么做 review**。
> 第一份 review 报告见 `REVIEW.md`，做你自己的判断前先读它。

---

## 0. 你是谁，你在做什么

你同时戴 4 顶帽子：

| 帽子 | 职责 |
|------|------|
| **产品 CEO** | 这工具值不值得继续投入？定位是否清晰？放弃什么、坚持什么？ |
| **产品经理** | 用户旅程是否顺？哪些功能是核心、哪些是噪声？MVP 的边界在哪？ |
| **设计主管 (UX)** | 命令名 / 错误提示 / 心智模型是否清晰？新人 5 分钟内能走通吗？ |
| **开发主管** | 模块边界是否合理？技术债大小？哪些重构 ROI 高？测试是否够？ |

每顶帽子产出独立一节，最后整合成统一建议。

**不要只戴一顶帽子。** 只看代码风格的 review 是失败的 review。

## 1. 必读上下文（先读，不读不许动手）

### 项目原始诉求（来自作者）

> "AutoDL 上做 ComfyUI / AIGC 创作。最痛的不是 clone 代码，是新实例起来后恢复模型、节点、工作流、配置和路径。
> 实例可能 15 天不开就被释放。
> **模型本体几十 GB，绝不能自动下载，必须用户主动**。
> aria2 是实测最稳的，HF Hub / hf_xet 在 AutoDL 实测连不上。"

### 核心设计原则（不可违反）

| 原则 | 解释 |
|------|------|
| **lock 不是下载源** | `model-lock.yaml` 是"曾经有什么 + 指纹"，不是"现在去下"的任务表 |
| **下载永远手动** | 5–30GB 单模型自动下载是反人类设计 |
| **数据盘是事实，系统盘是临时** | 任何只在系统盘的状态视为可丢失 |
| **secrets 不入 git** | 已有 `.gitignore` 保护，新功能必须保持 |
| **个人工具优先于通用平台** | 优雅但破坏一键体验 = 反向收益 |

### 必读文件清单（按顺序）

1. `README.md` — 用户视角
2. `CONTRIBUTING.md` — 开发者视角
3. `REVIEW.md` — 第一份 review 报告（v2 修正版）
4. `src/main.py` — 入口
5. `src/core/interface.py` + `src/core/artifacts.py` — 核心抽象
6. 7 个插件的 `plugin.py` + `manifest.yaml`
7. `src/lib/network/` — 整个网络子系统
8. `src/lib/download/manager.py` + `aria2.py`
9. `src/addons/models/lock.py` + `downloader.py`

读完后能回答：

- 7 个插件分别管什么，谁依赖谁
- `setup` / `start` / `sync` 各做什么
- mihomo 和 turbo 的 fallback 关系
- model-lock.yaml 在哪里写、在哪里读、是否一致

## 2. 多视角 Review 矩阵

### 2.1 产品 CEO 视角

**关注点**：定位、边界、长期方向、投入产出比。

**必答问题**：

1. 这工具今天解决的最大痛点是什么？一句话能说出来吗？
2. 如果这工具明天消失，作者要花多少时间重建创作环境？
3. 同等功能的开源 / 商业替代品是什么？为什么不直接用它们？（**必须做竞品扫描**）
4. 项目应该走哪条路：
   - 个人工具更可靠？
   - AutoDL ComfyUI 工作站管理器？
   - 跨平台 AIGC 工作区？
5. 哪些功能是"看起来重要、其实可以砍"的？
6. 哪些功能是"看起来不重要、其实是命门"的？

**输出**：一页定位陈述（300 字内），明确什么是核心、什么是装饰、什么是反模式。

### 2.2 产品经理视角

**关注点**：用户旅程、场景排序、MVP 边界。

**必做的事**：

1. 画 6 条用户旅程图，标出每一步的"摩擦点"：
   - 首次安装
   - 日常启动
   - 主动下载模型
   - 关机前
   - 实例被释放后新实例恢复
   - 出错诊断
2. 对每个摩擦点判断：是工具能解决的、还是 AutoDL 平台限制的、还是用户教育问题
3. 把所有功能按 "用户每周触达频率" × "失败时的痛感" 排成 RICE 矩阵
4. 找出 **3 个被低估的高价值动作**（成本低、价值大但目前没做）
5. 找出 **3 个被高估的低价值动作**（投入大、用户感知弱）

**输出**：用户旅程图 + RICE 矩阵 + 高/低估清单。

### 2.3 设计主管 (UX) 视角

**关注点**：命令名、错误提示、心智模型、信息密度。

**必做的事**：

1. 让一个**没用过这工具的 ComfyUI 用户**读 README，记录他每个困惑点（用 talk-aloud 法）
2. 列出所有 CLI 命令，给每条评分：
   - 命令名是否自解释（0–5）
   - 错误时是否给出下一步建议（0–5）
   - 是否有进度可见（0–5）
   - 是否能 `--help` 看懂（0–5）
3. 检查所有 `logger.error / warning` 输出，是否包含：
   - 出了什么事
   - 为什么会发生
   - 用户应该怎么办
4. 找出所有"隐式行为"（用户不知道工具在做什么）
5. 评估"恢复链路是否给用户安全感"——新实例上跑 `init.sh` 时，用户是否清楚自己处在哪一步、能否中断、能否回滚

**输出**：UX 问题清单 + 错误提示改写示例 + 命令命名建议表。

### 2.4 开发主管视角

**关注点**：模块边界、技术债、测试覆盖、重构 ROI。

**必做的事**：

1. 画当前模块依赖图，标出循环依赖 / 隐式耦合
2. 找出所有"双源真相"（同样的逻辑写在两个地方）
3. 评估每个插件的 SOLID：
   - 单一职责被破坏的地方
   - 依赖倒置是否到位（看 `src/core/ports.py`）
   - 是否有不必要的继承
4. 评估测试金字塔：
   - 单元 / 集成 / 端到端比例
   - 哪些关键路径**完全没测试**（重点检查 sync 链路、网络 fallback、lock 一致性）
5. 给每个建议的重构标注 ROI：
   - 改动大小（行数 / 文件数）
   - 价值（修 bug / 减少维护 / 启用新能力）
   - 风险（破坏现有行为的概率）
6. 列出 **不应该重构** 的地方（成熟、稳定、改了反而坏）

**输出**：依赖图 + 技术债清单（按 ROI 排序）+ 测试缺口表 + 不动清单。

### 2.5 加帽：SRE / 安全 / DX（轻量）

每个角色至少给出 3 条最关键发现，不展开。

| 角色 | 至少检查 |
|------|---------|
| **SRE** | 状态一致性 / 失败重试 / 日志可观测性 / 资源占用 |
| **安全** | secrets 是否真的安全 / SSH key Base64 风险 / git push 误同步风险 / root 权限边界 |
| **DX** | 文档与代码一致性 / 上手成本 / 贡献者门槛 |

## 3. 网络搜索任务包（必须做）

不查就乱给建议是最大的反模式。下面这些题目**必须用网络搜索**，并把检索结果作为论据写进 review。

### 3.1 AutoDL 平台事实核查

| 题目 | 检索关键词建议 | 期望产出 |
|------|----------------|----------|
| 实例多久不开机会被释放 | "AutoDL 实例释放 时长 数据盘" | 准确天数 + 释放策略 + 数据盘是否一并清理 |
| 6006 / 6008 端口映射协议 | "AutoDL 自定义服务 6006 端口映射 HTTP TCP" | 是否要求监听 0.0.0.0 / 是否限制协议 / 是否要 Nginx |
| 系统盘 / 数据盘默认容量 | "AutoDL 系统盘 容量 数据盘 扩容" | 准确数字 + 扩容方式 + 是否计费 |
| `/etc/network_turbo` 加速哪些域名 | "AutoDL 学术加速 GitHub HuggingFace 域名" | 加速白名单 + 是否覆盖 huggingface.co + civitai.com |
| 关机 / 释放 / 删除 三种状态区别 | "AutoDL 关机 释放 区别 计费" | 状态机图 + 计费规则 + 数据保留情况 |
| 无卡模式限制 | "AutoDL 无卡模式 价格 GPU 限制" | 价格 + 是否能装驱动 + 限制清单 |
| 预装 PyTorch / CUDA 版本 | "AutoDL 镜像 PyTorch CUDA 版本" | 当前主流镜像版本矩阵 |

### 3.2 ComfyUI 生态调研

| 题目 | 期望产出 |
|------|----------|
| ComfyUI Manager 快照机制最佳实践 | 官方文档 + 已知坑（snapshot 失败原因） |
| comfy-cli 当前命令清单与版本 | 看 `comfy --help` 是否有比项目更晚出的能力（如 `comfy install`、`comfy node restore-snapshot`） |
| 社区是否有现成的"ComfyUI 备份 / 恢复"工具 | **竞品扫描**：项目名 + 能力对比 + 优劣 |
| ComfyUI 模型路径配置（extra_model_paths.yaml）现状 | 是否仍是推荐方案 vs 软链接方案 |
| workflow 中的模型引用解析 | 节点 widget 的命名规则，能否静态分析出依赖模型 |

### 3.3 下载方案实测对比

| 题目 | 期望产出 |
|------|----------|
| aria2 / hf_transfer / hfd / wget 在国内 / AutoDL 的实测对比 | 速度 + 稳定性 + 是否需要科学 |
| HF_ENDPOINT=hf-mirror.com 当前是否可用 | 镜像状态 + 是否有限速 + 备选镜像 |
| CivitAI API token 限速规则 | 速率限制 + 是否需要登录 cookie |
| `huggingface_hub` 是否支持 aria2 backend | 验证 README 描述错误的修复路径 |

### 3.4 网络方案

| 题目 | 期望产出 |
|------|----------|
| mihomo（Clash.Meta）在 root Linux 的部署最佳实践 | systemd vs 直接进程 / 端口规范 / 配置安全 |
| Clash 订阅 URL 安全性 | URL 一旦泄露的影响 + 短期 token 方案 |
| AutoDL 是否限制对外代理 | TOS 检查 + 实测可行性 |

### 3.5 安全 / 凭据

| 题目 | 期望产出 |
|------|----------|
| SSH 私钥 Base64 存 yaml 的风险评估 | 对比 `ssh-add` / `gpg encrypted` / `1password CLI` 等方案 |
| GitHub deploy key vs PAT vs SSH key 在 CI / 一次性实例的最佳选择 | 推荐方案 + 撤销机制 |
| `.gitignore` 漏 secrets 的真实事故案例 | 至少 3 个案例 + 对项目的启示 |

### 3.6 竞品 / 参考项目（必须做的扫描）

至少调研以下方向：

- "ComfyUI portable / installer / launcher"
- "stable diffusion model manager"
- "AutoDL ComfyUI 镜像 / 一键脚本"
- "RunPod ComfyUI template"（看跨平台方案怎么做）
- "vast.ai ComfyUI bootstrap"

每个调研对象产出：

- 项目名 + 链接 + star 数
- 能力交集 / 差异
- 它做对了什么、做错了什么
- 是否有可借鉴的设计

**网络搜索的产出格式**：单独一节叫 `## 附录 A：事实核查与外部调研`，列出每条结论 + 至少 1 条来源链接。没有来源的结论不能出现在主报告里。

## 4. 边界框架（决策时反复回看）

所有 review 建议必须落到下面四个格子之一：

```
                  ┌─────────────────────┬─────────────────────┐
                  │   高用户价值        │   低用户价值        │
                  ├─────────────────────┼─────────────────────┤
   低实施成本     │   立刻做（A）       │   不做（C）         │
                  ├─────────────────────┼─────────────────────┤
   高实施成本     │   排期评估（B）     │   坚决拒绝（D）     │
                  └─────────────────────┴─────────────────────┘
```

### 必须做（强制项）

- AutoDL 数据盘 / 系统盘边界
- 实例释放后清单仍可见（lock 进 git 同步）
- secrets 不入 git
- 一键 `init.sh` 体验不能破坏
- 错误提示给出下一步建议

### 坚决不做（禁止项）

- setup / start 流程中自动批量下载模型
- 把 lock 当任务源
- 把模型本体进 git
- 把工具改成需要长期维护的通用 SaaS（除非作者明确转向）
- 引入新的运行时依赖（数据库、消息队列、Web 后端等）做这个项目本不该做的事

### 待评估（Open Questions）—— review 必须明确指出

- ComfyUI 装系统盘还是数据盘？
- 是否提供 Web UI 仪表板？
- 是否提供模型仓库 / 索引？
- 是否提供"按 workflow 自动算依赖模型"能力？
- 是否值得抽象出跨平台层？
- 是否提供云端备份 / sync 集成（rclone / OSS / S3）？

每个 Open Question 必须有：

- 现状描述
- 至少 2 个可选方向 + 各自代价
- reviewer 的倾向 + 理由
- 留给作者拍板的明确决策点

## 5. 高价值优化的发现框架

不要靠灵感，用框架。

### 5.1 用户 Job-to-be-Done 法

对每个核心场景问：

- 用户**雇这个工具来做什么 job**？（不是功能，是 job）
- 这个 job 的**进度感**是怎样的？（用户怎么知道在前进）
- 这个 job 的**结束信号**是什么？（用户怎么知道做完了）
- 哪一步是**最容易让用户放弃**的？

### 5.2 痛点放大法

把每个已知问题放到**最坏场景**下：

- 用户在凌晨 2 点赶稿、AutoDL 实例被释放、新实例 GPU 不一样
- 用户带 50G 模型、磁盘还剩 5G、网络抖动
- 用户配了 secrets 但忘了 userdata_repo
- 用户想撤销上一次 sync

哪些痛点在最坏场景下变成**项目价值毁灭性打击**？这些是真正的 P0。

### 5.3 竞品 Gap 分析

调研产出之后回答：

- 我们能做、别人不能做的（差异化护城河）
- 别人能做、我们不能做的（差距追赶 vs 战略放弃）
- 别人和我们都能做、但都做得烂的（机会区）

### 5.4 数据驱动假设法

提出每个新功能时附加：

- 这个功能服务什么场景？该场景一周触达几次？（频率假设）
- 没有这个功能时用户怎么办？（替代成本）
- 有了这个功能后，能省多少时间 / 减少几次失败？（收益假设）
- 这些假设可以怎么验证？（验证方案）

不能填上述 4 项的需求，**默认拒绝**。

## 6. 提出新需求建议的方法

### 6.1 RFC 模板（每个新需求一份）

```markdown
# RFC-XXX: [需求名]

## 背景
什么场景遇到什么问题。引用源码或日志为证。

## 用户价值
job-to-be-done + 频率 + 替代成本。

## 提议
具体做什么。给出最小可工作版本（MVP）。

## 非目标
明确不做什么。重点：是否会被滥用为"自动下载"等违反原则的操作。

## 替代方案
至少 2 个，并说明为什么本方案更好。

## 影响面
- 改动模块
- 新增依赖（重点）
- 用户行为变化
- 文档变化

## 风险
- 破坏现有体验的可能
- AutoDL 平台兼容性
- 安全 / 隐私风险

## 验收标准
怎么知道做对了。
```

### 6.2 优先级排序方法

对每个 RFC 计算 **RICE 分数**：

```
RICE = (Reach × Impact × Confidence) / Effort
```

- Reach：每周触达次数（用户实际用频率，不是理论上）
- Impact：1=微小, 2=小, 3=中, 5=大, 10=巨大
- Confidence：0–100% 你对前三项判断的把握
- Effort：人天

低于 5 的 RFC 直接砍。

### 6.3 推荐重点关注的方向（参考、不强制）

下面是第一份 review 没充分挖的方向，下一个 reviewer 应主动调研：

| 方向 | 待回答 |
|------|--------|
| **资产分级备份** | 工作流、配置、清单 → git；模型 → 用户外部；中间地带（节点源码 fork、自训练 LoRA）应该怎么管？ |
| **workflow 静态分析** | 能否解析 `.json` workflow 自动算出依赖模型？做了之后 `model status` 能多准确？ |
| **新实例感知** | 能否在 `init.sh` 启动时清楚地展示 "你处在 [全新实例 / 老实例重启 / 数据盘恢复]"？ |
| **跨实例 / 跨账号迁移** | 用户从 AutoDL A 账号迁到 B 账号，工具能帮多少？ |
| **失败模式编目** | 列出所有可能的失败：网络断、磁盘满、key 失效、权限错误、依赖冲突。每种失败的"用户该怎么办"是否都已经在错误信息里？ |
| **节点版本锁定** | `nodes/manifest.yaml` 只记 git URL 不记 commit。换实例后节点行为可能变化。要不要锁 commit？ |
| **`bye` 命令的事务性** | sync 中途失败时（git push 失败 / 网络断），状态如何回滚？是否会出现"快照写了但 git 没推"？ |
| **可观测性** | 一次 `init.sh` 跑了多久？哪一步最慢？有无指标可量化？ |
| **冷启动时间预算** | 新实例从启动到 `start` 成功的总时间预算应该是多少？分配给哪些步骤？ |
| **多 ComfyUI 实例** | 用户能否在一台 AutoDL 上跑多份 ComfyUI（不同 workflow 目录）？ |

## 8. 反模式清单（不要这么 review）

| 反模式 | 解释 |
|--------|------|
| 只看代码风格 | 类型注解、命名、docstring 已经很好，纠结这个浪费 |
| 不读源码先下结论 | 第一份 review 的 v1 就栽在这（误判 HF Hub 策略） |
| 凭"行业最佳实践"重构 | 个人工具不是企业服务，best practice 经常反向 |
| 用通用平台思路改造个人工具 | 引入数据库 / Web UI / 用户系统都是过度设计 |
| 把 AutoDL 当普通 VPS | 实例释放、端口映射、双盘结构是核心约束 |
| 提需求不附 RFC | 拍脑袋提需求是噪声 |
| 给建议不给 ROI | 没法决策 |
| 不做竞品扫描 | 重新发明轮子的源头 |
| 不指出前任错误 | review 的价值之一是纠错 |
| 全盘肯定或全盘否定 | 都说明没看仔细 |

## 10. 与作者沟通的方式

在你写 review 过程中，主动和作者确认这些：

1. **定位拍板**：定位 A / B / C 选哪个？
2. **资源边界**：作者愿意每月投入多少小时维护？
3. **用户边界**：除了作者自己还服务谁？
4. **不可触碰**：哪些设计是作者已经反复测试过、不许动的？（aria2、不自动下载等）
5. **反馈节奏**：是一次性交付还是迭代？

不要默默写完一份 reviewer 自嗨的报告。**review 是对话，不是独白。**
